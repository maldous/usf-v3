## 16. Collaboration and developer-like iteration

### 16.1 Functions, not roles

Collaboration functions are dynamic:

```text
interpret
decompose
propose
implement
challenge
review
repair
synthesize
```

No provider is permanently planner, reviewer or final authority.

### 16.2 Useful diversity

Use different providers for independent proposals or review when it increases expected value. Do not require every model to review every output.

A contributor must not be the sole reviewer of its candidate when an independent eligible reviewer exists. A provider is credited with material contribution only when its contribution digest is retained by the accepted candidate, its review finding causes an accepted change or refusal, or its proof-relevant analysis is explicitly referenced. Merely receiving the same prompt does not count.

### 16.3 Iterative workspace sessions

A writing model must be able to behave like a developer inside a mediated isolated workspace:

```text
inspect
reason
edit
run focused checks
fail
diagnose
edit again
review
refactor
run broader checks
produce final candidate
```

There is no semantic publication, signature, global proof, branch or commit between every iteration.

A candidate workspace provides write isolation without requiring a Git branch, worktree or commit. A Git integration worktree, branch and commit are created only at a coherent integration checkpoint.

### 16.4 Resolution

Deterministically combine disjoint contributions first.

Use model-assisted resolution for overlapping reasoning only. An unresolved blocker prevents integration. Validation, not model confidence, decides survival.
