
different obligations. The former warrants an exact bounded realisation; the
latter evaluates the realised bytes and feeds later acceptance, reproof or
remodel. A permission MUST NOT depend on the completion observations that can

## 1. North Light

USF V3 succeeds by increasing the rate at which valid semantic intent becomes valid ANQR realisation.

The primary authority loop is:

```text
semantic model
  → deterministic remodel and scoped currentness
  → admitted evidence
  → deterministic proof
  → activated contract and exact realisation permission
  → bounded work graph
  → eligible zero-paid-cost provider/model routes
  → parallel reasoning, implementation and critique
  → resolved candidate realisations
  → iterative engineering in isolated workspaces
  → deterministic validation observations
  → admitted evidence and reproof when applicable
  → significant semantic learning, when genuinely required
```

The pre-realisation evidence and proof establish that the exact model,
obligations, applicability, currentness and permission warrant construction.
Post-realisation validation closes or challenges those obligations and feeds
the next loop. These are related evidence cycles, not a licence to build first.

V3 does not succeed merely by producing:

- another semantic graph;
- another orchestration platform;
- another provider catalogue;
- another proof cockpit;
- another governance environment;
- a demonstration in which several models only discuss a design;
- a demonstration that stops before working, tested ANQR deliverables exist.

Every substantial capability must be justified by at least one concrete answer:

1. it interprets an ANQR requirement;
2. it constructs an ANQR deliverable;
3. it validates an ANQR deliverable;
4. it converts an ANQR result into evidence or proof;
5. it permits more eligible providers or models to contribute safely;
6. it removes a measured bottleneck from the realisation path.

“Enterprise-grade”, “future-proof”, “production-grade” and “we may need it later” are not sufficient justifications.

## 7. Formal semantic model

This section is normative. It removes ambiguity about authority, currentness, parallelism, publication and acceptance.

### 7.1 State domains

Let:

- `S` be the tracked authored semantic source selected by `graph/manifest.json`;
- `D(S)` be the deterministic derived closure of `S`;
- `C(X)` be canonical RDF dataset serialization of `X` partitioned by named graph;
- `H(X)` be SHA-256 over canonical bytes;
- `A(S) = H(C(D(S)))` be the global semantic revision digest;
- `R` be a repository realisation state represented by Git tree plus scoped file digests;
- `O` be factual observations;
- `E = N(O, requirement)` be normalized evidence satisfying an evidence schema;
- `P = Eval(obligation, E)` be deterministic proof evaluation;
- `M_t` be the provider/model routes eligible at time `t`;
- `W_t` be the actionable work graph at time `t`;
- `χ` be one explicit realisation chain.

The same semantic bytes at different Git commits have the same semantic revision digest. Git is a carrier and history mechanism, not the semantic identity function.

Semantic state, realisation state and operational working state are distinct authority classes. Movement between them is explicit:

- semantic source authorises and constrains;
- realisation source attempts to satisfy;
- operational artefacts coordinate and observe;
- normalized proof-relevant evidence may be promoted into semantic source only through `usf publish`.

An operational file does not become evidence, and implementation does not become semantic truth, merely because another file references it. Promotion copies/serializes the accepted normalized content and provenance into tracked source; canonical authority never depends on an ignored object path.

### 7.2 Semantic source and candidate deltas

A candidate semantic delta `δ` is evaluated as:

```text
S' = apply(S, δ)
A' = A(S')
```

`δ` may be validated, queried, reviewed and used in an isolated chain without first creating a Git commit.

A candidate delta is not canonical authority until `usf publish` validates and atomically applies it to the designated semantic source workspace.

A Git commit records a coherent durable checkpoint after one or more compatible semantic publications. It is not required after each triple, candidate, observation or proof result.

### 7.3 Significance predicate

A semantic delta is significant exactly when at least one predicate is true:

```text
Significant(δ) :=
    changesRequiredObservableBehaviour(δ)
 OR changesAcceptanceCriteria(δ)
 OR changesConstraintOrPermission(δ)
 OR changesObligationApplicability(δ)
 OR changesDurableConceptIdentityOrRelationship(δ)
 OR recordsAcceptedProductDecision(δ)
 OR admitsEvidenceThatChangesProofConclusion(δ)
 OR correctsSemanticContradictionOrOmission(δ)
```

The following alone are not significant:

- refactoring;
- renaming a test or file without semantic effect;
- provider availability or quota change;
- a different model answer;
- a routine test run;
- package upgrade without changed required behaviour;
- an intermediate source edit;
- a rejected candidate;
- operational scheduling or retry state.

Only significant deltas or evidence that changes a durable proof conclusion enter canonical semantic source.

### 7.4 Fine-grained dependency currentness

A global authority digest is recorded for audit, but it MUST NOT be the sole acceptance boundary for all work.

Every work packet and downstream artefact has a dependency set:

```text
Dep(x) =
    semantic resource or named-graph digests actually read
  + repository file pre-image digests actually read or writable
  + relevant policy/schema/tool-version digests
  + provider catalogue/probe digests where applicable
```

Its scoped dependency digest is:

```text
SD(x) = H(canonicalSort(Dep(x)))
```

An artefact is fresh when every member of `Dep(x)` still matches.

```text
Fresh(x, current) ⇔ ∀ d ∈ Dep(x): current(d.key) = d.digest
```

An unrelated repository or graph change MUST NOT invalidate `x` merely because the global Git tree or global semantic digest moved.

A global change to ontology, vocabulary, shared constraints, manifest semantics or another declared transitive dependency may invalidate broad scope because it appears in `Dep(x)`.

Adversarial tests MUST prove both:

- relevant dependency movement invalidates;
- unrelated movement does not invalidate.

### 7.5 Work graph and independence

Actionable work is represented as a directed acyclic graph:

```text
G_W = (V, E)
```

where vertices are work packets and edge `u → v` means `v` depends on accepted output from `u`. If semantic decomposition produces a dependency cycle, either collapse the strongly connected component into one composite atomic work packet or report a semantic decomposition defect; do not schedule a cyclic graph as if it were ready.

For work packet `w`, define:

- `Read(w)` — repository and semantic read set;
- `Write(w)` — permitted repository or semantic write set;
- `Dep(w)` — exact currentness dependencies;
- `Accept(w)` — deterministic acceptance criteria;
- `Value(w)` — sum of graph-declared weights for acceptance criteria newly closed by an accepted result; each criterion defaults to weight `1` when no explicit priority is declared. Model self-assessment cannot alter the weight.

Two work packets are parallel-compatible when:

```text
Independent(a,b) ⇔
    Write(a) ∩ Write(b) = ∅
 AND no unresolved semantic dependency edge exists between them
 AND neither changes a shared transitive dependency of the other
```

Read-only work may run concurrently without write isolation.

Writing work receives separate workspaces unless `Independent` and the implementation explicitly proves a shared workspace safe. The default is separate workspaces.

The dependency-ready set at time `t` is the maximal set of vertices whose
declared work dependencies are accepted and whose scoped inputs are fresh.
It is not yet the realisation-ready set. Realisation readiness additionally
requires one exact graph-derived current basis, declared applicability,
required admitted evidence, passing current proof and proof-warranted
permission through the requested ceiling. A narrowly graph-declared bootstrap
exception may permit isolated local check-only construction of the gate that
enforces this rule; it grants no provider contact, integration, publication,
runtime activation or completion authority.

### 7.6 Chains

A chain `χ` is an explicit content-addressed artefact graph associated with one semantic objective. It may branch and converge.

A chain contains references to:

- starting semantic revision and scoped dependency digest;
- work packet;
- routes and assignments;
- provider contributions;
- critiques;
- candidate workspaces or patches;
- checks;
- observations;
- evidence;
- proof;
- final disposition.

A chain is not:

- a global state machine;
- a lease or generation;
- a semantic graph node by default;
- a reason to block unrelated chains.

Chain stage is derived from valid artefacts, not trusted from one mutable status field.

A chain directory SHOULD use the following explicit layout:

```text
.usf/chains/<chain-digest>/
├── manifest.json
├── work.json
├── assignments.jsonl
├── contributions.jsonl
├── reviews.jsonl
├── candidates/
├── checks/
├── observations/
├── evidence/
├── proofs/
└── disposition.json
```

Files are immutable once referenced by digest. A corrected result is a new object/reference, not an in-place rewrite of historical bytes. Human run labels may point to chain digests but never determine identity.

Killing a process does not require replay. On restart, V3 scans valid artefacts, scoped claims, Git and semantic source to recompute ready work.

### 7.7 Realisation acceptance

A candidate `k` is accepted for integration only when:

```text
Accepted(k) ⇔
    schemaValid(k)
 AND realisationBasisCurrent(k)
 AND constructionAndActivationEligible(k)
 AND scopedDependenciesFresh(k)
 AND authorizedWriteSet(k)
 AND noUnresolvedBlocker(k)
 AND deterministicChecksPass(k)
 AND observedDiffEqualsWorkspaceState(k)
 AND zeroSecretLeakage(k)
```

Model agreement is neither necessary nor sufficient.

### 7.8 Evidence and proof

An observation is factual output.

Evidence is an observation normalized to an explicit evidence requirement with exact provenance and currentness.

Proof evaluates exact evidence against an explicit obligation.

```text
Evidence(o,r) ⇔ schemaValid(o) ∧ satisfiesProvenance(o,r)
ProofPass(p) ⇔ algorithm(p)(exactEvidenceSet(p), obligation(p)) = pass
```

Silence, missing applicability, stale evidence, sibling-obligation evidence, failed checks and model approval cannot imply proof success.

### 7.9 Optimization objective

Safety and semantic correctness are constraints, not optimization variables.

Within those constraints, scheduling uses lexicographic objectives:

1. maximize graph-weighted acceptance criteria closed per wall-clock time;
2. maintain exactly zero paid cost;
3. minimize critical-path latency;
4. maximize useful provider diversity;
5. maximize useful free-token throughput;
6. minimize repeated input tokens through bounded context and caching;
7. minimize serialized integration and publication time.

Raw model-call count and raw token volume are not success measures.

A token is useful when it belongs to an actionable chain and materially contributes to an accepted candidate, a defect found, a repair, or a proof-relevant conclusion. Probe and malformed-call tokens are reported separately.

The following invariants must hold at every accepted boundary:

```text
I09  Provider models cannot directly mutate canonical graph or primary source.
I10  Candidate writes are isolated, contained and derived from explicit scope.
I11  Integration and publication locks are narrow, local and short-lived.
I12  Independent work proceeds while unrelated work integrates or publishes.
I13  Observation, evidence, validation and proof remain different artefact kinds.
I14  Missing applicability, evidence or proof never implies success.
I15  Routine operational state does not enter semantic authority.
I16  Only Significant(delta) is eligible for canonical semantic publication.
I17  All mutable runtime state remains beneath USF_ROOT.
I18  Historical sources are never runtime dependencies.
```

### 8.2 Primary implementation

Use TypeScript, Node.js and pnpm.

Use a pnpm workspace only when multiple actual packages/apps exist; do not create speculative package boundaries.

### 8.3 Commodity infrastructure

USF owns semantics, work projection, collaboration, realisation, validation, evidence and proof.

It does not own the general provider ecosystem.

Use maintained third-party capabilities behind narrow replaceable interfaces:

- models.dev for model and provider-route metadata;
- Vercel AI SDK and maintained provider packages for protocol translation;
- OpenAI-compatible provider support where appropriate;
- Oxigraph JavaScript as the initial repository-contained RDF/SPARQL implementation, replaceable if the capability spike fails;
- a maintained SHACL implementation meeting the required fixture profile;
- a maintained RDF Dataset Canonicalization implementation;
- JSON Schema validation;
- standard Git for source history and integration.

At Gate 1, run a bounded dependency capability spike and pin exact current package versions in `pnpm-lock.yaml`. If a selected package does not satisfy the required fixture profile, replace it with the smallest maintained alternative and record the decision.

The initial provider adapter surface SHOULD cover OpenAI-compatible routes plus direct Google, Groq, Cerebras, Mistral and OpenRouter routes when corresponding zero-cost credentials/entitlements exist. Install only adapters needed by current configured routes; do not make this list a semantic roster or a completion denominator. Add other maintained AI SDK adapters dynamically when credentials and active work justify them.

Do not introduce LiteLLM, Portkey, Bifrost or another provider gateway/control plane unless direct AI SDK integration fails a recorded requirement and the gateway is demonstrably smaller than custom replacement work.

### 8.4 No semantic provider catalogue

The canonical graph expresses required model capabilities, privacy and cost constraints. It does not copy the global provider/model catalogue.

Provider catalogues, health and quota are operational observations beneath `.usf/`.

## 10. Semantic authority and lifecycle

### 10.1 Authority definition

USF V3 semantic revision identity is the canonical content digest `A(S)` defined in Section 7.

Tracked source is the durable carrier. The Git tree containing that source is recorded for provenance but does not alter semantic identity when the semantic bytes are unchanged.

Distinguish:

- `localSemanticRevision` — the validated semantic source bytes in the designated integration workspace, which may include an uncommitted compatible publication batch;
- `durableSemanticRevision` — the latest validated semantic source carried by an accepted Git commit.

Normal work may bind explicitly to either revision. A local revision is not fresh-clone durable until committed. `usf status`, work packets, publication receipts and terminal evidence must state which one they use. The terminal proof requires local and durable revisions to be equal.

The local semantic store is a disposable projection.

### 10.2 Semantic source

Tracked semantic source includes only durable meaning:

- ontology and vocabulary;
- contracts, requirements, constraints and acceptance criteria;
- explicit obligation applicability;
- significant realisation decisions;
- admitted proof-relevant evidence;
- proof definitions and accepted proof results where they alter durable conclusions;
- explicit claims, nonclaims and dispositions.

Do not place these in canonical semantic source by default:

- provider availability and quotas;
- prompts and model responses;
- work claims;
- retries;
- temporary patches;
- test logs;
- every implementation iteration;
- routine observations that do not affect proof or future semantic decisions.

### 10.3 Manifest and canonicalization

`graph/manifest.json` lists exact files, RDF formats, named graph IRIs, semantic roles and validation profiles.

The manifest does not contain its current authority digest.

Derivation MUST be deterministic, stratified or otherwise proven to terminate. Iterate to fixed point with a bounded maximum. Failure to converge is an error, not a new state.

Canonicalization and digests exclude timestamps, absolute paths, PIDs, run IDs, environment values, mutable provider metadata and self-referential digest records.

### 10.4 Minimum semantic kernel

Define only the concepts required by realisation:



### 10.5 Applicability

For each relevant obligation family, actionable contracts have exactly one state:

```text

```

Silence cannot mean not required.

### 10.6 Lifecycle

```text
Semantic Model
  → Remodel and Scoped Currentness
  → Admitted Evidence
  → Deterministic Proof
  → Activated Contract and Realisation Permission
  → Work Graph
  → Contribution
  → Candidate
  → Realisation
  → Validation Observation
  → Admitted Evidence / Reproof / Significant Remodel when applicable
```

No stage grants authority because a file or label claims the stage completed.
The authored contract definition is distinct from its proof-warranted active
permission. Every command from `work` through `check` carries or rederives
one immutable `RealisationBasis`; mixed, fabricated or stale bases refuse.
Pre-realisation construction evidence and proof gate the permission.
Post-realisation validation observations, completion evidence and completion
proof evaluate the result without participating in the permission that
authorised it.

## 11. Shared artefact contract

All command outputs use schema-defined canonical JSON or JSONL.

The minimum common envelope is conceptually:

```json
{
  "schema": "urn:usf:envelope:1",
  "kind": "work-packet",
  "producer": {
    "command": "usf work",
    "version": "..."
  },
  "identity": {
    "artifactDigest": "sha256:...",
    "chainDigest": "sha256:..."
  },
  "semantic": {
    "globalRevisionDigest": "sha256:...",
    "dependencyDigest": "sha256:...",
    "dependencies": []
  },
  "repository": {
    "carrierCommit": "...",
    "carrierTree": "...",
    "pathDependencies": []
  },
  "inputs": [],
  "payload": {},
  "metrics": {},
  "claims": [],
  "nonclaims": [],
  "createdAt": "RFC3339 UTC"
}
```

Rules:

- `createdAt`, local path and human run labels do not participate in semantic/artifact identity;
- every digestable structure uses canonical JSON;
- secrets and absolute paths are prohibited;
- requested and actual provider/model identity are separate;
- cost class, observed cost and usage are present for provider calls;
- failures use stable reason codes;
- raw provider responses are mode `0600`, secret-scanned and stored beneath `.usf/objects` or `.usf/chains`, never treated as authority.

Recommended exit codes:

```text

1 domain refusal, validation failure or proof failure
2 invalid CLI input or configuration
3 external catalogue/provider unavailable
4 currentness, integrity or drift failure
5 containment, privacy or security refusal
6 no eligible zero-paid-cost route
7 integration conflict
8 continuous supervisor degraded with no unsafe effect
```

## 12. Command surface

Expose one executable:

```bash
usf <command> [options]
```

Required commands:

```text
usf init
usf doctor
usf status
usf query
usf observe
usf metrics
usf work
usf models
usf probe
usf route
usf call
usf review
usf resolve
usf apply
usf check
usf integrate
usf evidence
usf prove
usf drift
usf publish
usf start
usf stop
usf watch
usf hermes
```

Every command MUST:

- have one primary responsibility;
- accept explicit files, stdin or JSONL;
- emit machine-readable output to stdout and diagnostics to stderr;
- avoid hidden global state;
- record exact inputs and scoped dependencies;
- be independently testable;
- be safe to retry when inputs are unchanged;
- avoid ANSI in machine mode;
- support repository-relative output paths;
- never require another command to have advanced a hidden lifecycle state.

The command registry is the single source for parsing and help. `usf --help`,
`usf help`, `usf help <command> [subcommand]` and
`usf <command> [subcommand] --help` MUST work without a repository, GitHub,
provider credentials, a supervisor or network access. Help states the purpose,
synopsis, bounded options, output schema, exit codes, implementation status,
external contact, history scan and authority/mutation effect for the selected
topic. Human help is text; `usf help ... --json` is stable machine-readable
metadata.

### 12.1 `usf init`

Create `.usf/`, verify containment, install/verify dependencies, retrieve catalogue snapshots, compile the local graph and contact no provider unless explicitly requested.

Idempotent.

### 12.2 `usf doctor`

Check Git identity, repository containment, package versions, `.env` tracking/mode, credentials by name only, graph capability, catalogue freshness, adapters, privacy policy, zero-cost policy, path/symlink safety and optional provider health.

### 12.3 `usf status`

Report observed state only: Git, semantic revision, store drift, current work graph, active chains, eligible routes, throughput, latest checks, integration queue and terminal-proof progress.

### 12.4 `usf query`

Read bounded semantic projections by IRI, contract, selector or SPARQL. Refuse mutation SPARQL. Emit truncation metadata. Produce fine-grained semantic dependency manifests.

### 12.5 `usf observe`

Produce factual observations for repository, graph, runtime, provider, validation and artefact state. Observation identity binds only observed facts, not summaries containing the observation identity.

### 12.5.1 `usf metrics`

Aggregate bounded operational history without becoming telemetry authority.
Keep `status` as the cheap current summary and `observe` as a point-in-time
factual observation. `metrics` reads explicit JSONL or ignored
`.usf/metrics/` records and exposes:

```text
usf metrics summary
usf metrics providers
usf metrics models
usf metrics tokens
usf metrics runs
usf metrics cache
usf metrics failures
usf metrics concurrency
```

Every view MUST accept bounded source and result limits, explicit time/run and
provider/model filters where applicable, and report input coverage,
truncation/incompleteness, numerators and denominators. Requested identity,
actual provider route and underlying model are separate dimensions. Missing
usage, cost, lineage, quota or identity is `unknown` / `not-observed`, never
zero. `T_useful` is reported only for tokens whose contribution digest is
referenced by accepted candidate, review, repair or proof-relevant lineage;
accepted adapter output alone is insufficient.

The command contacts no provider, GitHub or remote and performs no implicit
probe, publication, commit, push or semantic mutation. Operational events and
rollups contain no prompt/response bytes, credentials, endpoints, absolute
paths or unbounded labels. They are rebuildable local observations, not
evidence, proof, work completion or semantic source. Do not add a duplicate
`stats` alias or provider-specific top-level commands.

The bootstrap operator-observability slice implements help, broad `status` and
bounded `metrics`; it reserves `observe` as a distinct planned command for a
later graph-defined point-in-time observation slice rather than conflating it
with historical aggregation.

### 12.6 `usf work`

Derive the current work DAG and emit bounded work packets. Support:

```text
--ready
--selector
--stream
--shard
--max-items
```

A packet includes objective, semantic dependencies, read/write sets,
constraints, acceptance criteria, validation plan, evidence requirements,
proof obligations, contract permission, construction and activation
eligibility, immutable realisation basis, model capabilities, privacy, output
schema and graph-defined stop conditions.

No ticket is required. Dependency-ready alone is not semantic readiness. The
packet grants no authority beyond its exact current graph-derived basis and
permission ceiling.

### 12.7 `usf models`

Retrieve/normalize models.dev data, distinguish underlying model from provider route, report installed adapters and credentials by name, filter by capability/privacy/cost and maintain no independent hand-curated model database. Each chain/run freezes the exact raw catalogue snapshot digest and normalized-view digest it uses; a later refresh cannot silently alter an in-flight route decision.

### 12.8 `usf probe`

Perform bounded live capability and zero-cost verification. Probe lazily for active work, not every model before work begins. Record endpoint, actual provider/model, capability result, quota signal, usage and observed cost. Reject hidden paid fallback and unknown pricing.

### 12.9 `usf route`

Purely match semantically eligible work packets with current realisation bases
to fresh probe results and empirical validated performance observations.
Explain every inclusion/exclusion. Refuse external contact for proofblocked,
missing-evidence, failed-proof, stale or fabricated bases. Support diverse,
all-eligible, fastest, review-diverse and deterministic-fixture strategies.

Routing metrics are operational observations, not semantic authority or a fixed roster.

### 12.10 `usf call`

Invoke one or many assignments through the provider abstraction with provider-specific concurrency, bounded retries and `Retry-After` handling.

Every assignment carries explicit maximum turns, wall time, input/output tokens, tool calls and retry counts. A provider call is deduplicated by work-packet, route, prompt-template, tool-version and scoped dependency digests. Repeating an unchanged call requires `--force` or an explicit independence/freshness purpose.

Support two bounded modes:

1. `proposal` — return structured proposal, patch or file operations;
2. `workspace` — operate through a scope-checked tool broker in an isolated candidate workspace for developer-like iterative edit/test/repair.

Permitted broker tools may include read/search, typed write/patch and approved focused validation. Models receive no unrestricted shell, network, Git mutation, graph publication or secret access.

One workspace session may perform many edits and focused tests before any commit.

### 12.11 `usf review`

Create independent, risk-based review assignments. Review semantic coverage, implementation defects, security, tests, path scope, contradictions and claims. Use blocker/warning/note. Avoid all-to-all review and self-review when alternatives exist.

### 12.12 `usf resolve`

Resolve compatible contributions and reviews into one candidate using deterministic merge where possible and model-assisted synthesis only where reasoning is required. Preserve accepted/rejected lineage and unresolved findings. Do not write to a repository.

### 12.13 `usf apply`

Create or use an isolated candidate workspace materialised from the exact scoped base under `.usf/workspaces/<candidate-digest>/`. Candidate iteration MUST NOT require a Git branch, worktree or commit. Materialise with a repository-contained copy-on-write/reflink strategy where supported, otherwise a bounded copied snapshot; never use writable hard links to primary source. The workspace contains no usable primary `.git` control directory. Do not require the whole repository tree to be unchanged when unrelated paths changed. Derive the candidate change from actual pre/post file bytes, never model prose. `usf integrate` later applies the accepted typed delta to a short-lived Git integration worktree and derives the authoritative final diff from Git. Never modify the primary workspace during candidate execution.

### 12.14 `usf check`

Run affected checks during iteration and full checks at declared integration/publication/acceptance boundaries.

Checks include graph/schema/SHACL/integrity, format, typecheck, lint, unit/contract/integration tests, build, path scope, secret scan, generated freshness and planted defects.

Cache results by exact dependency digests. An unrelated change must not force unrelated expensive checks.

### 12.15 `usf integrate`

Integrate one or more checked candidates through standard Git.

Requirements:

- verify scoped dependencies and pre-images;
- batch candidates with disjoint or cleanly mergeable write sets;
- acquire one short repository-local integration lock only during primary-branch mutation;
- create a coherent Git commit, not one commit per model action;
- rerun affected checks after batch integration;
- schedule periodic/full checks by policy;
- leave conflicting candidates as explicit repair work;
- never create a second merge protocol.

Provider work and unrelated chains continue while integration waits.

### 12.16 `usf evidence`

Normalize observations and check results into evidence candidates. Promote only evidence required for a proof conclusion or durable future decision. Routine logs remain operational working state.

### 12.17 `usf prove`

Deterministically evaluate exact evidence against exact obligations with explicit applicability and scoped currentness. Distinguish pass, fail, blocked and unresolved. Do not modify source.

### 12.18 `usf drift`

Compare semantic source, derived store, graph-authorised realisation, Git implementation, accepted evidence and current observations. Report scoped and global drift. Do not repair.

### 12.19 `usf publish`

Validate and atomically apply one or more compatible significant semantic deltas to tracked graph source.

Requirements:

- validate candidate deltas without requiring prior commits;
- batch compatible deltas;
- lock only the affected publication scope or the brief final graph-source mutation;
- run affected graph checks first and complete graph gates at the publication boundary;
- rebuild from resulting tracked files;
- emit a publication receipt;
- create no implicit push or release;
- permit a later coherent Git checkpoint to contain several publications.

### 12.20 `usf start` and `usf stop`

Expose an explicit process lifecycle without creating a second scheduler,
authority plane or service manager.

`usf start` MUST:

- require an explicit versioned realisation profile and explicit
  repository-relative product manifest; bind the process-control identity to
  the profile selector, manifest selector, through boundary,
  tracked automation-policy digest and exact lifecycle-tool digest;
- record the global semantic revision and selected per-work scoped dependency
  digests as dynamic observations rather than process-wide invalidation keys;
  semantic or product-overlay movement rederives the selected work projection
  and re-evaluates only affected work rather than restarting the composer or
  requiring whole-run reproof;
- require no GitHub or Git-remote availability for local query, work,
  contribution, candidate, check or lifecycle progress. Local Git carrier
  identity may be observed, but commit batching and explicit push remain
  separate boundaries and remote failure cannot stop unrelated local work;
- acquire one exact instance-scoped, OS-released repository-local ownership
  lock before any provider contact and retain it while admitted work exists;
  this is neither a distributed lease nor a global lifecycle checkpoint;
- run the same composer as `usf watch` in the foreground, emit a
  machine-readable readiness record only after identity and policy checks pass,
  and leave backgrounding or restart policy to ordinary Unix process
  supervision;
- be retry-safe: an identical live instance reports `already-running`, while a
  conflicting live instance fails closed;
- keep all process records beneath ignored `.usf/runs`, mode-restricted and
  operational only. A running or ready record never establishes semantic
  completion, evidence or proof.

`usf stop` MUST:

- target an exact named instance, defaulting only to the unambiguous default
  instance;
- validate the complete recorded process identity and write an instance-bound
  graceful-stop intent beneath `.usf/` rather than signalling a PID blindly;
- stop new assignment admission, wait for bounded drain and return an explicit
  `stopped`, `already-stopped`, `degraded` or refused result;
- be idempotent, never signal an unrelated process, and leave forced
  termination to an explicit external-supervisor action. If admitted work
  ignores cancellation beyond the drain bound, return a degraded observation
  to the waiting stop command but retain instance ownership until that work
  actually settles or the external supervisor terminates the process;
- permit restart to quarantine demonstrably stale operational records and
  rescan current artefacts, Git and semantic source without replay.

Every executable or continuously operating deliverable MUST declare its start,
readiness, drain and stop contract. Pure libraries, metadata indexes and static
file artefacts declare lifecycle not applicable rather than gaining a
fictitious process. Lifecycle declarations grant no integration, publication
or runtime-provider authority.

### 12.21 `usf hermes`

Provide an optional Hermes-Agent management facade without creating another
composer or authority plane.

`usf hermes` MUST:

- resolve bare invocation to exactly one tracked, versioned default operating
  intent or refuse before provider or Hermes-Agent contact when the intent is
  absent, invalid or ambiguous;
- bind an exact USF core profile and manifest plus an exact selected-product
  profile and manifest, retaining separate core-to-product, product-to-core and
  composite content digests so unrelated movement does not require global
  reproof. ANQR is one product overlay, not a Hermes-only execution mode;
- invoke the same disposable foreground composer, lifecycle owner lock, stop
  intent, bounded drain and restart-by-rescan path used by `usf start` and
  `usf watch`; ordinary `usf stop --instance NAME` can stop the exact Hermes
  lifecycle instance;
- consume the same provider configuration, availability, economics,
  qualification, routing and concurrency decisions as ordinary USF commands,
  considering every currently configured and eligible route dynamically rather
  than maintaining a Hermes roster;
- preserve the live-provider sequence: trusted exact-account receipt,
  content-verified scrubbed adapter child, authenticated provider-produced
  answers, genuine hidden-holdout qualification, then live call and unattended
  composition;
- perform no credential lookup in the initial hermetic facade. Later live work
  names one exact repository-relative ignored owner-only credential file,
  never falls back to ambient inherited variables, and forwards at most the
  selected route's allowlisted variable through the same future scrubbed child;
  never copy or export the complete V3 credential environment to Hermes-Agent;
- keep Hermes optimization optional, asynchronous and bounded. It may propose
  prompt/context compression, agent roles, route mixtures, review, repair,
  batch cohorts and skill candidates, but failure, timeout or absence preserves
  the deterministic plan. A future Hermes call consumes its own visible
  assignment, provider slot and budgets, but cannot reserve unrelated slots or
  the `primary-mutation` lock. Every proposal binds the exact base plan, ready
  set, scoped dependencies, prompts, context, output, tools, skills and
  optimizer runtime, applies only to unclaimed work, and is ignored when late,
  stale or mismatched; it cannot cancel, duplicate or suppress assignments;
- keep one stable closed policy envelope tracked, while each AI-tuned resolved
  instance configuration is schema-validated, fully input-digest-bound and
  atomically stored owner-only beneath ignored `.usf/runs/hermes/`. Status and
  restart rederive it from tracked authority rather than trusting ignored
  state; routine tuning creates no Git commit or semantic publication;
- treat generated skills as isolated, versioned candidates that require normal
  validation, independent review and later graph-authorized activation. A live
  run cannot hot-mutate active instructions, tools, qualifications, acceptance
  or authority;
- require no Docker daemon, GitHub, hosted or self-hosted runner, external CAS,
  database, Stardog, V1/V2 checkout or separate repository for deterministic
  help, doctor, lifecycle, fallback, restart or verification.

Hermes may propose coherent commit or publication batches, but USF decides
eligibility from checked candidates, fresh scoped dependencies, compatible
write sets and validation boundaries, unresolved blockers and rollback scope.
A chain stage is not automatically a commit boundary. Every flush is limited
by the selected `through` ceiling and tracked automation policy. At `check`,
stop leaves checked candidates queued and performs no integration, commit or
publication. At an explicitly authorized higher ceiling, flush on
coherent-unit closure, risk/diff/age ceilings, explicit checkpoint or stop
drain, with no minimum batch size that can starve a lone accepted candidate.

Hermes is never required to select a product. Ordinary `usf start` can select
the USF-only profile, ANQR profile or any later product profile directly. A
different product may provide a different versioned operating intent and
stable Hermes policy configuration while using the same optional facade.

The initial Hermes slice may prove only local configuration, provider
population evaluation, deterministic fallback and foreground start/status/stop
through fixtures. It MUST NOT claim that Hermes-Agent ran, that a provider was
contacted, live parallelism or semantic-token reduction, production BAU, full
ANQR, staging, production or terminal proof without the exact evidence.

### 12.22 `usf watch`

Provide continuous foreground semantic realisation without introducing a second authority or workflow engine.

`watch` MUST:

- repeatedly derive ready work from current graph/repository/evidence;
- launch bounded independent chains through the same command contracts;
- use provider-specific queues and host/resource caps;
- allow multiple watch processes to cooperate through short-lived repository-local atomic claims;
- derive completion from valid artefacts, integration and semantic state;
- release claims automatically on process exit where the host supports file locks;
- recover after restart by rescanning explicit artefacts rather than replaying events;
- isolate provider and candidate failures;
- idle when no useful work exists rather than fabricate activity;
- support `--through check`, `--through integrate` and `--through publish`;
- default to `--through check`; integration or publication requires explicit CLI selection and tracked automation policy;
- use bounded idle backoff rather than busy polling;
- handle SIGINT/SIGTERM by stopping new assignments, allowing bounded in-flight artefacts to finish or time out, and releasing local claims;
- preserve every failed chain for diagnosis;
- stop safely on containment, privacy, cost or integrity refusal.

`watch` is a disposable composer. Killing it must not require a recovery protocol.

## 13. Provider and zero-paid-cost architecture

### 13.1 Availability tuple

`free` is not a timeless model property.

At time `t`, an eligible route is the tuple:

```text
provider route
+ underlying model
+ installed adapter
+ credential or entitlement
+ required capability
+ privacy permission
+ current quota
+ current health
+ zero-paid-cost policy
+ observed actual identity
```

### 13.2 Cost classes

```text
local
zero-price
free-quota
subscription
paid
unknown
```

The V3 terminal proof accepts only `local`, `zero-price` and `free-quota`.

Default policy:

```text
maximum paid cost = 0
paid fallback = prohibited
unknown price = ineligible
router alias capable of paid fallback = ineligible
```

Subscription routes may be supported separately but do not count toward the free-provider proof.

A route is zero-paid-cost eligible only when its frozen invocation evidence proves the exact cost basis. Acceptable bases are exact zero-price metadata, a documented free-quota entitlement with remaining allowance, or local inference. Promotional/one-time credit, unknown billing state and a router capable of paid fallback are not accepted unless the operator explicitly classifies that credit as a bounded zero-paid-cost source for a non-terminal experiment; such an experiment does not satisfy the terminal proof. When a provider reports usage cost, observed cost must be zero. When it does not, exact route and entitlement evidence must remain current and no paid credential/fallback may be configured.

### 13.3 Independent provider family

For the terminal proof, an independent provider family is a distinct mandatory inference control plane and credential/entitlement boundary. Multiple models or upstream routes reached only through one gateway count as one provider family. OpenRouter free routes therefore demonstrate model diversity but count as one provider family. A direct Groq route and an OpenRouter route count as two families even if they can serve the same underlying model, because removal of one control plane leaves the other.

The acceptance bundle records both provider-family diversity and underlying-model-family diversity. Neither substitutes for the other.

### 13.4 Dynamic population

Do not hard-code two or three providers.

For each active work capability set:

1. enumerate every configured route;
2. filter by installed adapter, credential, privacy and catalogue facts;
3. probe every remaining bounded candidate unless a fresh valid probe exists;
4. record exact exclusion reasons;
5. route useful work to every successfully eligible provider/model subject to declared provider/host caps;
6. require at least two independent provider families for the live acceptance proof;
7. repeat after excluding one previously successful provider.

One unavailable or exhausted route removes capacity only. It does not stop unrelated routes.

### 13.5 Adaptive routing without admission bureaucracy

Do not create a permanent admission roster.

Maintain repository-local operational observations of validated task outcomes, latency, token usage, provider errors and cache behaviour.

Routing may use those observations as explicit inputs. It must remain explainable and reproducible from its input snapshot.

Probe lazily. Do not fully qualify the universe before useful work begins.

## 14. Massive parallelism and continuous operation

### 14.1 Meaning of massive

“Massively parallel” means the architecture has no fixed small model or chain limit and useful throughput increases as independent work and eligible routes increase until declared host/provider limits are reached.

It does not mean sending every prompt to every model.

Parallelise by:

- semantic requirement;
- artefact;
- package/component;
- repository path;
- test obligation;
- review dimension;
- implementation hypothesis;
- independent provider route.

### 14.2 Scheduling constraints

For assignment binary variable `x(w,m)`:

```text
x(w,m) = 1 when work packet w is assigned to route m
```

Assignments MUST satisfy:

```text
capabilities(m) ⊇ requirements(w)
privacy(m) permits classification(w)
cost(m,w) = 0
freshProbe(m,w)
providerConcurrency(m) not exceeded
hostConcurrency not exceeded
no prohibited write conflict
```

The scheduler SHOULD select assignments maximizing the objective in Section 7.9. It MUST prevent starvation by aging ready work and MUST maintain provider fairness so one fast route cannot consume every suitable packet when diversity or quota utilization would create higher expected value. Speculative duplicate assignments require an explicit diversity/review rationale and a bounded duplication budget.

### 14.3 Concurrency target

At each scheduling point:

```text
C_target = min(
    ready independent work,
    sum of eligible provider concurrency caps,
    configured host/model concurrency cap,
    memory/process safety cap
)
```

Report:

```text
C_observed
C_target
parallel utilisation = active invocation time / (elapsed × C_target)
```

Provider waiting, integration and semantic publication must not hold unrelated provider slots.

### 14.4 Local claims, not distributed leases

To prevent duplicate mutation on one host, V3 MAY use OS-released file locks or atomic repository-local claim creation keyed by work/route/workspace digest.

Such a claim:

- is transient operational working state;
- grants no semantic or integration authority;
- carries no fencing token;
- is released or invalidated when the owning process is gone;
- cannot block unrelated scope;
- is reconstructed or removed safely at startup.

Do not generalize this into a distributed lease system.

### 14.5 Continuous proof

The terminal proof includes a continuous run that:

- processes at least three successive ready-work batches without manual stage advancement;
- contains multiple simultaneous chains;
- survives one forced watch-process restart;
- survives one injected provider failure and one rejected candidate;
- continues unrelated work during those failures;
- integrates at least one coherent batch;
- publishes at most the significant semantic learning required by the accepted work;
- records zero paid cost.

## 15. Token and context economy

### 15.1 Bounded packets

Models receive the smallest sufficient packet:

- objective;
- relevant semantic identities and requirements;
- scoped source excerpts or read tools;
- permitted writes;
- acceptance and validation;
- output schema;
- claims/nonclaims and stop conditions.

Do not send full graph, full repository, conversation history, unrelated logs, provider catalogue or previous reasoning.

### 15.2 Cache identity

Cache model and deterministic results by material inputs, including:

```text
semantic dependency digest
work packet digest
repository path dependency digest
prompt-template digest
provider and actual model
adapter/tool version
required capability set
```

Do not repeat a model call when all material inputs are unchanged and a valid result remains reusable, unless explicitly running an independence or freshness experiment.

### 15.3 High-token objective

V3 must be capable of exploiting high aggregate free-token capacity when useful ANQR work exists.

Define:

```text
T_useful = input + output tokens from calls that contribute to accepted work,
           actionable defect discovery or accepted repair
T_total  = all provider input + output tokens
Yield    = graph-weighted accepted value / T_total
```

A call is counted as useful only when its contribution digest is referenced by an accepted candidate, an accepted review finding, an accepted repair lineage or a proof-relevant conclusion. Unreferenced alternatives, probes and malformed responses remain in `T_total` but not `T_useful`.

Before the live proof begins, compute and freeze:

```text
T_target = min(operator target, evidenced free capacity, useful ready-work demand)
```

The default operator target is `1,000,000` aggregate useful tokens. The terminal proof requires `T_target ≥ 100,000` and requires the frozen target to be achieved. A target below the default is permitted only when the pre-run provider census and real ANQR work graph independently demonstrate the constraint. Free-capacity evidence must come from current quota/rate-limit metadata, provider responses or a conservative operator cap; model prose is not evidence. Where exact token quota is unavailable, calculate a conservative bound from the declared run duration, provider request/token limits and work budgets. Do not lower the target after observing the run, substitute paid capacity, repeat duplicate prompts or fabricate work merely to accumulate tokens. If evidenced zero-paid-cost capacity is below 100,000 useful tokens, the high-token terminal proof is blocked rather than waived.

The architecture scale test MUST simulate at least `10,000,000` accounted tokens through fake providers to prove that token accounting, fanout, caching and aggregation do not require external capacity.

Record gross token throughput, useful token throughput, cache reuse and yield. A system that achieves correctness only by repeatedly sending enormous duplicate contexts has failed.

### 15.4 Deterministic work before model work

Use deterministic tools for inventories, graph derivation, source search, digests, schema validation, patch application, test execution and mechanically compatible merge.

Use models for interpretation, design, implementation, critique, repair and genuine ambiguity.

### 16.1 Functions, not roles

Collaboration functions are dynamic:

```text

decompose
propose
```

No provider is permanently planner, reviewer or final authority.

### 16.2 Useful diversity

Use different providers for independent proposals or review when it increases expected value. Do not require every model to review every output.

A contributor must not be the sole reviewer of its candidate when an independent eligible reviewer exists. A provider is credited with material contribution only when its contribution digest is retained by the accepted candidate, its review finding causes an accepted change or refusal, or its proof-relevant analysis is explicitly referenced. Merely receiving the same prompt does not count.

```text

run focused checks
fail
diagnose

review
refactor

```

There is no semantic publication, signature, global proof, branch or commit between every iteration.

A candidate workspace provides write isolation without requiring a Git branch, worktree or commit. A Git integration worktree, branch and commit are created only at a coherent integration checkpoint.

### 16.4 Resolution

Deterministically combine disjoint contributions first.

Use model-assisted resolution for overlapping reasoning only. An unresolved blocker prevents integration. Validation, not model confidence, decides survival.

## 17. Git and integration semantics

Git is used for:

- durable source history;
- coherent checkpoints;
- reviewable diffs;
- integration and release provenance;
- recovery.

Git is not:

- the semantic clock;
- task queue;
- model communication bus;
- run ledger;
- proof engine;
- required boundary after every edit.

### 17.1 Commit policy

Create commits for coherent durable units, such as:

- repository bootstrap;
- one accepted ANQR slice or coherent part thereof;
- one reusable V3 tool capability;
- one compatible batch of validated candidates;
- one coherent batch of significant semantic/evidence publication;
- one correction with its regressions.

Do not create commits for individual prompts, reviews, rejected candidates, test failures, retries, semantic triples or chain stages.

### 17.2 Scoped rebasing

A candidate does not become stale merely because an unrelated commit landed.

`usf apply` and `integrate` compare exact scoped path pre-images and semantic dependencies. If they remain unchanged, the candidate may be applied/rebased and rechecked without repeating provider work.

### 17.3 Integration bottleneck control

Integration and semantic publication are inherently single-writer at the exact designated source-workspace mutation instant. They share one repository-local `primary-mutation` lock and MUST NOT acquire nested mutation locks in conflicting order. All preparation and validation occurs before acquiring it; post-mutation affected verification occurs after the smallest necessary atomic write/commit step where safe. Keep the lock narrow.

Prepare, validate and queue candidates in parallel. Batch independent changes. Measure mutation-lock duration and queue delay. Continue unrelated read/provider/workspace work while the lock is held.

## 19. Security, privacy and egress

Every work packet declares one classification:

```text
public
private-metadata
private-source
restricted
```

Tracked provider policy declares what each route may receive.

Default:

- external free routes: `public` only;
- explicitly approved routes: `public` and possibly `private-metadata` or `private-source` according to recorded terms;
- local routes: policy-defined;
- `restricted`: local-only.

The first live multi-provider ANQR slice MUST be public-safe or use routes explicitly approved for its classification. Repository privacy does not automatically mean every source byte may be sent externally.

Prompt construction sends only exact permitted excerpts. It never sends `.env`, full repository archives, full graph, unrelated source, previous transcripts or secret-bearing logs.

Real credentials exist only in `.env` mode `0600` or isolated `.usf/home`, are gitignored, allowlisted, never printed and never passed wholesale to provider subprocesses.

All provider input and output receives secret-pattern scanning and path/provenance recording sufficient to audit egress without exposing secret values.

### 19.1 Two-trust execution boundary

Provider invocation and candidate execution are separate processes with separate authority:

- the provider-invocation process may receive only the credential variables required by the selected route and may not execute candidate code;
- the candidate-validation process receives no provider credentials, no `.env`, no provider home and no unrestricted network or filesystem access.

`usf check` MUST execute model-produced code through a proven confinement adapter. The initial implementation SHOULD use the Node.js permission model for Node-only commands when it can deny filesystem access outside the worktree/run temporary directory, deny credential paths and deny network/child-process access except explicit allowlists. If the required command cannot be confined by the selected adapter, automatic execution is refused until a proven local sandbox is available or the command is explicitly reviewed and allowlisted.

Sanitizing environment variables alone is not sufficient confinement because candidate code runs as the same host user.

Adversarial validation MUST attempt to:

- read `.env`;
- read `.usf/home`;
- read historical source paths;
- write outside the candidate worktree;
- access the network when not allowed;
- spawn an unapproved child process;
- exfiltrate secret-shaped canary values.

All attempts must fail without weakening unrelated validation.

### 19.2 Dependency and install safety

A model may propose dependency changes but may not install arbitrary dependencies directly.

Dependency candidates must declare package, version/range, purpose and licence. Integration checks lockfile reproducibility, registry provenance, licence policy, known security findings where available and install-script posture. Default installation uses ignored scripts; a package requiring an install script needs explicit tracked approval and a confined test.

No package manager process executing candidate-controlled hooks receives provider credentials.

Test:

- missing authority/dependency provenance;
- stale relevant source;

- superseded/invalidated evidence;
- missing applicability;
- proof inferred from absence;
- server statistic alters authority identity;
- self-referential digest;
- forged stable flag;

```text

256 independent work packets
32 concurrent calls or the host safety cap, whichever is lower
10,000,000 accounted tokens
provider failure injection
watch-process restart
candidate rejection
integration batching
```

For fixed-latency fake work, measure speedup:

```text
speedup(k) = elapsed(1 worker) / elapsed(k workers)
```

For `k ∈ {2,4,8}` supported by the host, require:

```text
speedup(k) ≥ 0.60 × k
```

or produce a measured bottleneck finding, correct it and rerun. Do not waive the result by narration.

Every critical rule has a planted defect that fails for its intended stable reason, not an unrelated parse error.

### 22.7 Test portfolio economics

The full no-force-exit suite remains the authoritative local gate. Named unit,
contract, integration, lifecycle, adversarial and scale lanes exist for focused
iteration; they never waive the full gate at integration, publication or
acceptance. Every test owns one distinct semantic acceptance/refusal,
serialization invariant or real process boundary. When a new lower-cost test
subsumes an existing assertion, prune the duplicate in the same change.

runtime roots. Do not grow Cartesian per-command matrices, wall-clock sleeps,
network/GitHub dependencies, hidden flaky retries or repeated scale fixtures.
Ignored repository-local caches, including any future `.usf/objects` adapter,
MUST be reconstructable from tracked inputs or explicit test fixtures. Tests
MUST pass from a clean clone with an empty `.usf/`, MUST NOT require a warm CAS
or GitHub-hosted cache, and MUST exercise any future content-store invariants
locally before merely repeating them in optional hosted CI. No self-hosted
GitHub runner is a V3 prerequisite.
Establish duration budgets from at least ten clean runs on the same host class,
record p95 and slowest files, and treat a regression as a measured bottleneck.
Do not use forced test-runner exit because it can conceal leaked descriptors or
child processes.
